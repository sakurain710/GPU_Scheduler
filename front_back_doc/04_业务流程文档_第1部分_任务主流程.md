# 业务流程文档（第1部分）：任务主流程（提交→排队→调度→执行→完成/失败）

## 1. 文档目标
- 说明 GPU 任务从提交到完成/失败的端到端业务流程。
- 给出页面操作与后端接口、服务、调度组件之间的调用关系。
- 标注关键状态流转与异常分支（审批、超时、重试、DLQ）。

## 2. 涉及模块
- 接口层：`GpuTaskController`
- 业务层：`GpuTaskService`
- 调度层：`TaskDispatcher`、`TaskAssignmentService`、`TaskPriorityQueue`、`TaskStateMachine`、`TaskAgingScheduler`
- 执行监控：`TaskExecutionSimulator`、`TaskCompletionMonitor`
- 失败处理：`TaskRetryDlqService`
- 通知：`TaskNotificationService`

## 3. 主流程（成功路径）

### 3.1 前端提交任务
1. 页面提交任务表单，调用：`POST /api/tasks/submit`（兼容 `/api/task/submit`）。
2. `GpuTaskService.submitTask` 执行提交策略校验：
- 非审批角色用户的活动任务数上限（默认 3）。
- 高优先级任务（默认 `basePriority>=9`）是否需要审批。
3. 创建 `gpu_task` 记录。
4. 若不需审批：触发 `transition(taskId, QUEUED)`，写入优先队列。
5. 返回 `TaskResponse` 给前端。

### 3.2 调度器轮询分配
1. `TaskDispatcher` 按固定周期执行调度（默认 5 秒）。
2. 从 `TaskPriorityQueue` 出队任务 ID。
3. 校验任务仍处于 `QUEUED`，否则跳过。
4. `GpuAllocator.allocate(task)` 选择可用 GPU。
5. 若分配成功，调用 `TaskAssignmentService.assign(task,gpu)`：
- 原子将 GPU 从 `IDLE -> BUSY`。
- 计算 `estimatedSeconds` 与 `estimatedFinishAt`。
- 状态迁移 `QUEUED -> RUNNING`。
- 事务提交后把任务投递给 `TaskExecutionSimulator` 异步执行。

### 3.3 执行与完成回收
1. `TaskExecutionSimulator` 在线程池内模拟任务执行。
2. `TaskCompletionMonitor` 周期扫描 `RUNNING` 任务。
3. 任务正常完成时：
- 回写 `actualSeconds`。
- 状态迁移 `RUNNING -> COMPLETED`。
- 释放 GPU（`BUSY -> IDLE`）。
4. 每次状态迁移都会：
- 写入 `gpu_task_log` 审计记录。
- 触发任务状态通知。

## 4. 关键分支流程

### 4.1 审批分支（高优先级）
1. 满足“高优且无审批角色”时，任务初始状态为 `PENDING_APPROVAL`。
2. 审批人查看：`GET /api/tasks/approval/pending`。
3. 审批通过：`POST /api/tasks/{taskId}/approve`，状态 `PENDING_APPROVAL -> QUEUED`。
4. 审批拒绝：`POST /api/tasks/{taskId}/reject`，状态 `PENDING_APPROVAL -> REJECTED`。

### 4.2 无可用 GPU 分支
1. 调度时若无可用 GPU：
- 尝试抢占 `TaskPreemptionService.tryPreemptFor(task)`。
- 无论是否抢占成功，当前任务按有效优先级重新入队。
2. 连续失败达到阈值后，调度器进入退避轮次（backoff）。

### 4.3 执行失败/超时分支
1. `TaskCompletionMonitor` 判定执行超时（超过预估时间 2 倍）或执行失败。
2. 状态迁移 `RUNNING -> FAILED`，并释放 GPU。
3. 调用 `TaskRetryDlqService.onTaskFailed(taskId, reason)`：
- 未超过最大重试：进入重试计划队列（指数退避）。
- 超过最大重试：进入 DLQ（死信队列）。

### 4.4 重试与死信回放
1. `TaskRetryDlqService.processScheduledRetries` 定时扫描到期重试任务。
2. 满足条件（任务仍是 `FAILED`）时，迁移回 `QUEUED`。
3. 运维可通过 `/api/ops/dlq/{taskId}/reprocess` 手工回放 DLQ 任务。

## 5. 状态机约束（与主流程相关）
- `PENDING -> QUEUED/CANCELLED`
- `PENDING_APPROVAL -> QUEUED/REJECTED/CANCELLED`
- `QUEUED -> RUNNING/CANCELLED`
- `RUNNING -> COMPLETED/FAILED/QUEUED`
- `FAILED -> QUEUED`
- 终态：`COMPLETED/FAILED/CANCELLED/REJECTED`（除 `FAILED` 外不可再迁移）

## 6. 页面与接口关系
- 任务提交页：`POST /api/tasks/submit`
- 我的任务页：`GET /api/tasks/my`、`GET /api/tasks/{taskId}`
- 任务取消操作：`POST /api/tasks/{taskId}/cancel`
- 审批页：`GET /api/tasks/approval/pending`、`POST /approve`、`POST /reject`
- 运维故障处理页：`/api/ops/*`（DLQ、强制重入队、强制失败、抢占）

## 7. 风险与边界
- 当前执行为模拟器执行（`TaskExecutionSimulator`），不是实际 GPU 任务运行时。
- `task_type` 在 DB 有枚举约束，提交值需严格符合数据库取值。
- 状态迁移由 `TaskStateMachine` 强校验，前端应按 `errorCode` 处理非法状态操作。
