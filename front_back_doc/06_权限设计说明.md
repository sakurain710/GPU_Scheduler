# 权限设计说明

## 1. 文档目标
- 统一描述当前后端权限体系与生效机制。
- 明确前端联调时的权限判断口径与未实现边界。

## 2. 登录认证方式

### 2.1 认证模式
- `✅ 已实现` 基于 JWT 的无状态认证（`SessionCreationPolicy.STATELESS`）。
- `✅ 已实现` 登录入口：`POST /api/auth/login`（用户名密码）。
- `✅ 已实现` 刷新入口：`POST /api/auth/refresh`（refresh token）。
- `✅ 已实现` 登出入口：`POST /api/auth/logout`（令牌拉黑）。

### 2.2 用户状态约束
- `✅ 已实现` 用户状态在 `CustomUserDetails` 中参与认证判定：
- `status=1` 视为启用
- `status=2` 视为锁定（`isAccountNonLocked=false`）

## 3. Token 使用方式

### 3.1 Token 结构与用法
- `✅ 已实现` 请求头：`Authorization: Bearer <accessToken>`。
- `✅ 已实现` 区分 access/refresh 两类 token。
- `✅ 已实现` `JwtAuthenticationFilter` 仅允许 access token 进入鉴权上下文。

### 3.2 黑名单与撤销
- `✅ 已实现` Token 黑名单（Redis）
- `✅ 已实现` refresh 后可撤销某用户指定时间前签发的 access token。
- `⚠️ 待确认` Redis 不可用时采用 fail-open（鉴权可继续），是否满足生产安全策略。

### 3.3 安全过滤链
- `✅ 已实现` 过滤器顺序：`IdempotencyFilter -> RateLimitFilter -> JwtAuthenticationFilter -> UsernamePasswordAuthenticationFilter`。
- `✅ 已实现` 未授权入口统一返回 `401 + AUTH_UNAUTHORIZED`。

## 4. 接口权限设计

### 4.1 全局路由访问策略
- `permitAll`：`/api/auth/**`、`/api/public/**`、`/actuator/health`、`/v3/api-docs/**`、`/swagger-ui/**`、`/ws/**` 等。
- 其余路由：`authenticated()`。

### 4.2 Authority 组装策略
- `✅ 已实现` 每次请求按 userId 从数据库加载：
- 角色码（如 `ROLE_ADMIN`）
- 权限码（如 `task:approval:review`）
- `✅ 已实现` `CustomUserDetails` 合并角色码与权限码进入 `GrantedAuthority`。

### 4.3 接口权限矩阵（按模块）

| 模块 | 路径前缀 | 鉴权规则 |
|---|---|---|
| 认证 | `/api/auth/*` | 路由放行；业务接口内做 token 语义校验 |
| 用户管理 | `/api/users/*` | `ROLE_ADMIN` 或 `user:manage` |
| 角色管理 | `/api/roles/*` | `ROLE_ADMIN` 或 `role:manage` |
| RBAC字典 | `/api/rbac/*` | `ROLE_ADMIN` 或 `rbac:read` |
| GPU管理-写 | `/api/gpu(s)` 写操作 | `ROLE_ADMIN` 或 `gpu:write` |
| GPU监控读 | `/api/gpu(s)/health|metrics` | `ROLE_ADMIN` 或 `gpu:read` |
| GPU心跳 | `/api/gpu(s)/*/heartbeat` | `ROLE_ADMIN` 或 `gpu:heartbeat` |
| 任务审批查询 | `/api/task(s)/approval/pending` | `ROLE_ADMIN` / `ROLE_TASK_REVIEWER` / `task:approval:read` |
| 任务审批操作 | `/api/task(s)/*/approve|reject` | `ROLE_ADMIN` / `ROLE_TASK_REVIEWER` / `task:approval:review` |
| 运维控制 | `/api/ops/*` | `ROLE_ADMIN` 或 `ops:manage` |
| 监控接口 | `/api/health`、`/api/metrics` | `ROLE_ADMIN` 或 `monitoring:read` |

### 4.4 任务对象级权限
- `✅ 已实现` 任务详情/取消存在“所有者或审批角色”校验（`TASK_FORBIDDEN`）。

## 5. 菜单权限设计

### 5.1 当前实现状态
- `✅ 已实现` 数据模型已具备（`resource` 表支持菜单/API/按钮/数据类型）。
- `✅ 已实现` 后端已提供“菜单树按当前用户可见权限裁剪”接口：`GET /api/rbac/me/menu-tree`。

### 5.2 前端联调建议
- 优先使用后端返回的菜单树作为菜单渲染主数据源（`/api/rbac/me/menu-tree`）。
- 字典数据来源：`/api/rbac/resources`（默认 `status=1`）可用于管理页配置与校验。
- 菜单树返回的是按用户当前权限裁剪后的可见菜单，前端不应再额外放宽显示范围。

## 6. 按钮权限设计

### 6.1 当前实现状态
- `✅ 已实现` 权限码可参与接口鉴权（`@PreAuthorize`）。
- `✅ 已实现` 已提供“按钮级权限清单按用户聚合返回”接口：`GET /api/rbac/me/button-permissions`。

### 6.2 前端联调建议
- 按 `/api/rbac/me/button-permissions` 返回的权限码渲染按钮可用性（如 `task:approval:review`、`ops:manage`）。
- 后端仍做最终鉴权，前端按钮控制仅作体验优化。

## 7. 数据权限设计

### 7.1 当前实现状态
- `✅ 已实现` 任务数据存在对象级限制：非审批角色仅可访问自己的任务。
- `❌ 未实现` 通用行级数据权限框架（如部门/租户/项目域过滤）尚未实现。
- `⚠️ 待确认` `resource.type=4(数据)` 仅为模型预留，当前无完整执行链路。

## 8. 权限生效机制
- `✅ 已实现` 权限变更后，后续请求实时加载用户角色/权限，通常无需重新登录。
- `⚠️ 待确认` 前端若缓存菜单/按钮权限，需要在授权变更后主动刷新本地缓存。

## 9. 风险项
- `[R1]` 前端若仅按角色渲染，不按权限码渲染，可能产生越权/漏权展示。
- `[R2]` `/api/auth/**` 路由放行易被误判为“无需token”，实际 `me/logout` 仍依赖有效token语义。
- `[R3]` Redis故障时黑名单与撤销检查 fail-open，安全策略需按环境评估。
