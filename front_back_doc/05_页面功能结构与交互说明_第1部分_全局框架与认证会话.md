# 页面功能结构与交互说明（第1部分）：全局框架与认证会话

## 1. 文档范围
- 本部分覆盖页面模块：
1. 登录页
2. 应用初始化与会话恢复
3. 全局导航与权限门禁
4. 会话续期与退出
- 不包含视觉设计，仅描述功能结构与交互行为。

## 2. 页面模块一：登录页（Auth Login）

### 2.1 页面结构（功能区域）
- 账号输入区：`username`
- 密码输入区：`password`
- 提交动作区：登录按钮
- 反馈区：登录错误提示、频控提示

### 2.2 展示数据来源
- 本地输入状态（前端表单模型）
- 后端响应：`LoginResponse`（token、用户基础信息、角色列表）

### 2.3 操作行为
1. 用户输入账号与密码后点击登录。
2. 前端调用 `POST /api/auth/login`。
3. 成功则保存 `accessToken/refreshToken` 并进入应用壳层。
4. 失败则按 `code/errorCode/message` 显示可操作提示。

### 2.4 状态变化
- `idle` -> `submitting` -> `success`（进入已登录态）
- `idle` -> `submitting` -> `error`（保留输入并显示错误）

### 2.5 接口依赖
- `POST /api/auth/login`
- 失败分支依赖统一错误码处理：`401`、`429`、`503`

## 3. 页面模块二：应用初始化与会话恢复（App Bootstrap）

### 3.1 页面结构（功能区域）
- 启动加载区：全局加载状态
- 身份探测区：当前用户信息拉取
- 路由决策区：进入业务页或回登录页

### 3.2 展示数据来源
- 本地 token 存储
- 后端响应：`GET /api/auth/me` 的 `UserResponse`

### 3.3 操作行为
1. 应用启动时读取本地 token。
2. 若存在 accessToken，调用 `GET /api/auth/me` 校验会话有效性。
3. 有效则注入全局用户上下文（id/username/roles/status）。
4. 无效则尝试刷新（`POST /api/auth/refresh`）；仍失败则跳转登录。

### 3.4 状态变化
- `booting` -> `authenticated`
- `booting` -> `refreshing` -> `authenticated`
- `booting` -> `unauthenticated`

### 3.5 接口依赖
- `GET /api/auth/me`
- `POST /api/auth/refresh`

## 4. 页面模块三：全局导航与权限门禁（Layout + Guard）

### 4.1 页面结构（功能区域）
- 顶部会话区：当前用户、退出入口
- 侧边导航区：业务模块入口
- 主内容区：子页面路由容器
- 全局消息区：统一错误提示

### 4.2 展示数据来源
- 当前用户上下文：`/api/auth/me`
- 权限映射来源：
- 角色/权限矩阵：`docs/rbac_permission_matrix.md`
- 运行时权限：token + 后端实时鉴权结果

### 4.3 操作行为
1. 根据用户角色/权限渲染可见菜单与操作入口。
2. 菜单数据优先取后端可见菜单树：`GET /api/rbac/me/menu-tree`。
3. 按钮可用性取后端聚合权限码：`GET /api/rbac/me/button-permissions`。
4. 点击导航切换到对应业务页面。
5. 若后端返回 `403`，页面显示“无权限”并保持当前路由可回退。

### 4.4 状态变化
- `menu_loading` -> `menu_ready`
- `route_enter` -> `authorized`
- `route_enter` -> `forbidden`

### 4.5 接口依赖
- 当前部分无新增接口；依赖各业务页接口鉴权返回。
- 建议前端在菜单层同时使用角色与权限码进行门禁。

## 5. 页面模块四：会话续期与退出（Session Lifecycle）

### 5.1 页面结构（功能区域）
- 会话状态区：token 过期提醒（可选）
- 操作区：主动退出
- 异常恢复区：自动续期与重登录跳转

### 5.2 展示数据来源
- token 到期信息（前端本地解析或被动依赖 401）
- 后端刷新响应：新 token 对

### 5.3 操作行为
1. 统一拦截器策略：请求遇到 `401/INVALID_TOKEN` 时，进入“单飞刷新（single-flight refresh）”。
2. 刷新成功：对排队中的原请求进行一次性重放。
3. 刷新失败：清理会话并跳转登录页，不做无限重试。
4. 用户主动点击退出：调用 `POST /api/auth/logout`。

### 5.4 状态变化
- `active` -> `refreshing` -> `active`
- `active` -> `refresh_failed` -> `logged_out`
- `active` -> `logging_out` -> `logged_out`

### 5.5 接口依赖
- `POST /api/auth/refresh`
- `POST /api/auth/logout`

## 6. 跨页面交互约束（本部分）
- 所有业务请求统一附带：`Authorization: Bearer <accessToken>`。
- 写操作建议统一附带：`X-Request-Id`，减少重复提交风险。
- 错误处理优先使用 `errorCode`，其次使用 `message`。

## 7. 结论
- `✅ 已确定` 前端采用“拦截器自动刷新 + 请求重放”统一处理 401，并限制为单次刷新。
- `✅ 已确定` 路由命名遵循后端资源语义的 `kebab-case` 规范：
- 示例：`/tasks`、`/tasks/approvals`、`/gpus`、`/admin/users`、`/admin/roles`、`/monitoring`。
- 推荐 API 路径统一使用复数资源风格：`/api/tasks`、`/api/gpus`（兼容别名仅保留兼容用途）。
