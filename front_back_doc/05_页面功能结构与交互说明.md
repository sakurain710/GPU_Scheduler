## 全局框架与认证会话


## 1. 文档范围
- 本部分覆盖页面模块：
1. 登录页
2. 应用初始化与会话恢复
3. 全局导航与权限门禁
4. 会话续期与退出
- 不包含视觉设计，仅描述功能结构与交互行为。

## 2. 页面模块一：登录页（Auth Login）

### 2.1 页面结构（功能区域）
- 账号输入区：`username`
- 密码输入区：`password`
- 提交动作区：登录按钮
- 反馈区：登录错误提示、频控提示

### 2.2 展示数据来源
- 本地输入状态（前端表单模型）
- 后端响应：`LoginResponse`（token、用户基础信息、角色列表）

### 2.3 操作行为
1. 用户输入账号与密码后点击登录。
2. 前端调用 `POST /api/auth/login`。
3. 成功则保存 `accessToken/refreshToken` 并进入应用壳层。
4. 失败则按 `code/errorCode/message` 显示可操作提示。

### 2.4 状态变化
- `idle` -> `submitting` -> `success`（进入已登录态）
- `idle` -> `submitting` -> `error`（保留输入并显示错误）

### 2.5 接口依赖
- `POST /api/auth/login`
- 失败分支依赖统一错误码处理：`401`、`429`、`503`

## 3. 页面模块二：应用初始化与会话恢复（App Bootstrap）

### 3.1 页面结构（功能区域）
- 启动加载区：全局加载状态
- 身份探测区：当前用户信息拉取
- 路由决策区：进入业务页或回登录页

### 3.2 展示数据来源
- 本地 token 存储
- 后端响应：`GET /api/auth/me` 的 `UserResponse`

### 3.3 操作行为
1. 应用启动时读取本地 token。
2. 若存在 accessToken，调用 `GET /api/auth/me` 校验会话有效性。
3. 有效则注入全局用户上下文（id/username/roles/status）。
4. 无效则尝试刷新（`POST /api/auth/refresh`）；仍失败则跳转登录。

### 3.4 状态变化
- `booting` -> `authenticated`
- `booting` -> `refreshing` -> `authenticated`
- `booting` -> `unauthenticated`

### 3.5 接口依赖
- `GET /api/auth/me`
- `POST /api/auth/refresh`

## 4. 页面模块三：全局导航与权限门禁（Layout + Guard）

### 4.1 页面结构（功能区域）
- 顶部会话区：当前用户、退出入口
- 侧边导航区：业务模块入口
- 主内容区：子页面路由容器
- 全局消息区：统一错误提示

### 4.2 展示数据来源
- 当前用户上下文：`/api/auth/me`
- 权限映射来源：
- 角色/权限矩阵：`docs/rbac_permission_matrix.md`
- 运行时权限：token + 后端实时鉴权结果

### 4.3 操作行为
1. 根据用户角色/权限渲染可见菜单与操作入口。
2. 菜单数据优先取后端可见菜单树：`GET /api/rbac/me/menu-tree`。
3. 按钮可用性取后端聚合权限码：`GET /api/rbac/me/button-permissions`。
4. 点击导航切换到对应业务页面。
5. 若后端返回 `403`，页面显示“无权限”并保持当前路由可回退。

### 4.4 状态变化
- `menu_loading` -> `menu_ready`
- `route_enter` -> `authorized`
- `route_enter` -> `forbidden`

### 4.5 接口依赖
- 当前部分无新增接口；依赖各业务页接口鉴权返回。
- 建议前端在菜单层同时使用角色与权限码进行门禁。

## 5. 页面模块四：会话续期与退出（Session Lifecycle）

### 5.1 页面结构（功能区域）
- 会话状态区：token 过期提醒（可选）
- 操作区：主动退出
- 异常恢复区：自动续期与重登录跳转

### 5.2 展示数据来源
- token 到期信息（前端本地解析或被动依赖 401）
- 后端刷新响应：新 token 对

### 5.3 操作行为
1. 统一拦截器策略：请求遇到 `401/INVALID_TOKEN` 时，进入“单飞刷新（single-flight refresh）”。
2. 刷新成功：对排队中的原请求进行一次性重放。
3. 刷新失败：清理会话并跳转登录页，不做无限重试。
4. 用户主动点击退出：调用 `POST /api/auth/logout`。

### 5.4 状态变化
- `active` -> `refreshing` -> `active`
- `active` -> `refresh_failed` -> `logged_out`
- `active` -> `logging_out` -> `logged_out`

### 5.5 接口依赖
- `POST /api/auth/refresh`
- `POST /api/auth/logout`

## 6. 跨页面交互约束（本部分）
- 所有业务请求统一附带：`Authorization: Bearer <accessToken>`。
- 写操作建议统一附带：`X-Request-Id`，减少重复提交风险。
- 错误处理优先使用 `errorCode`，其次使用 `message`。

## 7. 结论
- `✅ 已确定` 前端采用“拦截器自动刷新 + 请求重放”统一处理 401，并限制为单次刷新。
- `✅ 已确定` 路由命名遵循后端资源语义的 `kebab-case` 规范：
- 示例：`/tasks`、`/tasks/approvals`、`/gpus`、`/admin/users`、`/admin/roles`、`/monitoring`。
- 推荐 API 路径统一使用复数资源风格：`/api/tasks`、`/api/gpus`。

## 任务中心与审批


## 1. 文档范围
- 本部分覆盖页面模块：
1. 任务提交页
2. 我的任务列表页
3. 任务详情页
4. 审批中心页（待审批任务）
- 仅描述功能结构与交互，不包含视觉设计。

## 2. 页面模块一：任务提交页（Task Submit）

### 2.1 页面结构（功能区域）
- 基础信息区：`title`、`description`、`taskType`
- 资源需求区：`minMemoryGb`、`computeUnitsGflop`
- 调度参数区：`basePriority`
- 提交动作区：提交按钮、重置按钮
- 反馈区：提交结果与错误提示

### 2.2 展示数据来源
- 前端表单状态
- 提交响应：`TaskResponse`

### 2.3 操作行为
1. 用户填写任务并提交。
2. 调用 `POST /api/tasks/submit`。
3. 根据响应状态进入两类结果：
- 普通任务：进入 `QUEUED`
- 高优任务且无审批权限：进入 `PENDING_APPROVAL`
4. 成功后跳转“我的任务”或进入任务详情。

### 2.4 状态变化
- `editing` -> `submitting` -> `submitted`
- `editing` -> `submitting` -> `submit_failed`

### 2.5 接口依赖
- `POST /api/tasks/submit`
- 典型错误：`TASK_ACTIVE_LIMIT_EXCEEDED`、参数校验失败、限流错误

## 3. 页面模块二：我的任务列表页（My Tasks）

### 3.1 页面结构（功能区域）
- 过滤区：状态筛选、排序字段、排序方向
- 列表区：任务表格（状态、优先级、显存需求、创建时间等）
- 分页区：页码/每页大小
- 行操作区：查看详情、取消任务（按状态可见）

### 3.2 展示数据来源
- `GET /api/tasks/my` 返回 `IPage<TaskResponse>`

### 3.3 操作行为
1. 页面加载拉取当前用户任务分页。
2. 用户调整过滤条件后重新查询。
3. 点击某行进入详情页。
4. 对可取消任务执行取消操作。

### 3.4 状态变化
- `loading` -> `loaded`
- `loaded` -> `filtering` -> `loaded`
- `loaded` -> `cancelling` -> `cancelled`

### 3.5 接口依赖
- `GET /api/tasks/my?page&size&status&sortBy&sortDir`
- `POST /api/tasks/{taskId}/cancel`

## 4. 页面模块三：任务详情页（Task Detail）

### 4.1 页面结构（功能区域）
- 基础信息区：标题、类型、提交人
- 资源与调度区：优先级、显存需求、计算量、GPU绑定
- 执行进度区：状态、估算耗时、实际耗时、关键时间点
- 异常信息区：`errorMessage`
- 操作区：取消任务（权限与状态满足时）

### 4.2 展示数据来源
- `GET /api/tasks/{taskId}` 的 `TaskResponse`
- （可选）用户专属状态推送：`/topic/task-status/{userId}`

### 4.3 操作行为
1. 路由进入后拉取详情。
2. 若任务状态变化，刷新或实时更新页面状态。
3. 用户可在允许状态下取消任务。

### 4.4 状态变化
- `detail_loading` -> `detail_ready`
- `detail_ready` -> `status_updating` -> `detail_ready`

### 4.5 接口依赖
- `GET /api/tasks/{taskId}`
- `POST /api/tasks/{taskId}/cancel`

## 5. 页面模块四：审批中心页（Approval Center）

### 5.1 页面结构（功能区域）
- 筛选分页区：页码、每页大小、排序
- 待审批列表区：`PENDING_APPROVAL` 任务列表
- 审批动作区：通过、拒绝（拒绝原因输入）
- 处理反馈区：操作结果提示

### 5.2 展示数据来源
- `GET /api/tasks/approval/pending` 返回 `IPage<TaskResponse>`

### 5.3 操作行为
1. 审批人打开页面加载待审批任务。
2. 点击“通过”调用审批通过接口。
3. 点击“拒绝”填写原因并提交。
4. 操作成功后刷新列表并同步状态统计。
5. 支持对多选任务执行批量通过/批量拒绝。

### 5.4 状态变化
- `pending_loading` -> `pending_ready`
- `pending_ready` -> `approving` -> `approved`
- `pending_ready` -> `rejecting` -> `rejected`

### 5.5 接口依赖
- `GET /api/tasks/approval/pending`
- `POST /api/tasks/{taskId}/approve`
- `POST /api/tasks/{taskId}/reject`
- `POST /api/tasks/approval/batch/approve`
- `POST /api/tasks/approval/batch/reject`
- 权限要求：`ROLE_ADMIN/ROLE_TASK_REVIEWER/task:approval:*`

## 6. 跨页面交互规则（任务域）
- 任务状态以 `TaskStatus` 为唯一状态源，页面应按状态码渲染按钮可用性。
- 状态迁移受后端状态机约束，前端需处理 `INVALID_TASK_STATE`。
- 列表与详情之间需要共享任务ID与当前状态，避免多页状态不一致。

## 7. 已确认项
- “我的任务”列表自动轮询由前端按页面策略决定，不作为后端强制能力。
- 审批页需要批量审批，后端已提供批量通过/批量拒绝接口。

### 2.1 页面结构（功能区域）

### 3.1 页面结构（功能区域）

- `ops_idle` -> `action_running` -> `action_failed`
- `dlq_loading` -> `dlq_ready`

### 5.5 接口依赖

- `POST /api/ops/circuit-breaker/reset`

- `POST /api/ops/tasks/{taskId}/force-fail`
- `POST /api/ops/tasks/{taskId}/preempt`
- `POST /api/ops/queue/drain`
- `GET /api/ops/notification/webhook/retry/status`

## 6. 跨页面交互规则（GPU/运维域）

- GPU列表与运维操作台共享任务/资源状态源，操作后应联动刷新。

- 不引入“运维只读角色”，运维操作仍统一要求 `ops:manage` / `ROLE_ADMIN`。

## 用户角色与权限配置中心


## 1. 文档范围

3. 权限配置页（资源/权限字典）

## 2. 页面模块一：用户管理页（User Admin）

### 2.1 页面结构（功能区域）
- 检索区：用户名、邮箱、状态、排序
- 列表区：用户表格（用户名、邮箱、状态、角色、时间）

## 4. 页面模块三：权限配置页（RBAC Dictionary）

### 4.1 页面结构（功能区域）

2. 选择资源节点后查询对应权限。

## 5. 页面模块四：授权关系编辑弹窗

### 5.1 用户-角色绑定弹窗
- 目标：为指定用户配置角色集合。
- 提交接口：`POST /api/users/{userId}/roles`
- 交互要点：提交前展示“将覆盖用户现有角色”的确认。

### 5.2 角色-权限绑定弹窗
- 目标：为角色配置权限集合。
- 提交接口：`POST /api/roles/{roleId}/permissions`
- 交互要点：该接口为“覆盖写入”，提交需包含完整目标权限集。

### 5.3 角色-用户绑定弹窗
- 目标：把多个用户绑定到角色（可选过期时间）。
- 提交接口：`POST /api/roles/{roleId}/users`
- 交互要点：属于新增绑定；解除需走 `DELETE /users`。

## 6. 跨页面交互规则（RBAC域）
- 授权变更后建议刷新当前用户上下文和菜单缓存。
- 角色/权限配置页应按权限码渲染入口，兼容角色门禁。
- 错误处理优先读取 `errorCode`：如 `ROLE_IN_USE`、`RESOURCE_NOT_FOUND`、`DUPLICATE_RESOURCE`。

## 7. 状态与生效说明
- 后端每次请求会实时加载用户角色与权限码。
- 因此授权变更在后续请求可即时生效，不要求强制重新登录。
- 前端若做本地权限缓存，需在授权变更后主动刷新。

## 8. 已确认项
- 角色页“权限差异预览”暂不作为本轮必需能力。
- 不引入 RBAC 只读角色，角色与权限修改入口继续使用管理权限控制。
- `AssignUsersRequest/AssignPermissionsRequest` 的 `roleId` 一致性由前端执行强校验，后端以路径参数为准。

## 2. 页面模块一：系统健康总览页（Health Overview）

## 3. 页面模块二：任务与GPU监控大盘（Metrics Dashboard）

### 3.1 页面结构（功能区域）
- 任务概览区：队列长度、状态分布、完成率/失败率
- 排队分析区：优先级队列长度、等待时长分布、时延分位
- GPU概览区：总量、状态分布、利用率
- 资源分析区：显存占用/剩余、碎片率、空闲时长
- 任务流转区：实时任务表格（全局任务流）

### 3.2 展示数据来源
- `GET /api/metrics` -> `{ tasks, gpus }`
- `GET /api/metrics/tasks/stream?activeOnly=true` -> `IPage<TaskResponse>`（实时任务表格）
- 字段来源：`TaskMetrics`、`GpuMetrics`、`TaskResponse`

### 3.3 操作行为
1. 页面首屏并行拉取 `metrics` 与 `metrics/tasks/stream`。
2. `metrics` 填充 KPI 与图表，`metrics/tasks/stream` 填充实时任务表格。
3. 默认使用 `activeOnly=true`，仅展示排队中与运行中的任务。
4. 若显式传入 `status`，以后端 `status` 过滤结果为准。

### 3.4 状态变化
- `metrics_loading` -> `metrics_ready`
- `metrics_ready` -> `metrics_refreshing` -> `metrics_ready`

### 3.5 接口依赖

- `GET /api/metrics/tasks/stream`

## 4. 页面模块三：实时订阅管理（Realtime Channels）

### 4.1 页面结构（功能区域）
- 连接状态区：WebSocket连接状态、最近心跳时间
- 订阅控制区：订阅/取消订阅开关
- 实时事件区：最新遥测快照、任务状态变化事件流

### 4.2 展示数据来源
- WebSocket 连接端点：`/ws`（SockJS）
- Telemetry 主题：`/topic/telemetry`（`TelemetrySnapshot`）
- 用户任务状态主题：`/topic/task-status/{userId}`（`TaskStatusNotification`）

### 4.3 操作行为
1. 页面加载后建立 WebSocket 连接。
2. 订阅遥测主题并增量更新大盘。
3. 订阅用户任务主题并更新任务事件流或消息中心。
4. 断线时触发自动重连并回补一次 REST 请求。

### 4.4 状态变化
- `ws_disconnected` -> `ws_connecting` -> `ws_connected`
- `ws_connected` -> `subscribed`
- `ws_connected` -> `ws_error` -> `reconnecting`

### 4.5 接口依赖
- WebSocket STOMP：`/ws`
- Topic：`/topic/telemetry`、`/topic/task-status/{userId}`

## 5. 页面模块四：监控异常降级与重连处理

### 5.1 页面结构（功能区域）
- 降级提示区：实时通道不可用提示
- 恢复策略区：重连倒计时、手动重连按钮
- 数据一致性区：最近一次快照时间戳

### 5.2 展示数据来源
- WebSocket连接状态机（前端）
- `TelemetrySnapshot.timestamp`

### 5.3 操作行为
1. WebSocket失败时进入降级模式，仅保留 REST 定时拉取。
2. 达到重连条件时自动重连。
3. 重连成功后恢复实时更新并校正快照时间。

### 5.4 状态变化
- `realtime_mode` -> `degraded_mode`
- `degraded_mode` -> `recovery_check` -> `realtime_mode`

### 5.5 接口依赖
- 降级拉取：`GET /api/metrics`、`GET /api/metrics/tasks/stream`、`GET /api/health`

## 6. 跨页面交互规则（监控域）
- 监控页默认“REST首屏 + WebSocket增量”双通道策略。
- 实时推送异常时必须保留 REST 可用路径，避免页面空白。
- 任务页与监控页可共享任务状态事件总线，避免重复订阅。

## 7. 已确认项
- 刷新策略：`REST 首屏 + WebSocket 增量 + 固定 30s REST 校准`。
- 重连策略：指数退避 `1s/2s/4s/8s/16s`，上限 `30s`，最大重试 `10` 次；超限后进入降级模式并保留手动重连。
- 快照策略：前端仅保留最近 `200` 条 `TelemetrySnapshot` 于内存环形缓冲，不做本地持久化落库。
